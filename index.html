    A-01

    The Notebook

    A trading journal for MT5 traders: review fast, change one thing, see if it held. Every number on screen can be traced back to a broker record.

    Live denotebook.app ↗ Code: private repo

    The problem

    Most trading journals run on hand-typed numbers and screenshots, so their statistics can't be checked. A trader asking "did my change work?" gets an answer nobody can defend.

    What I built

    One language, one repository, two processes. A Next.js web app and a Node worker share 18 packages and meet only in PostgreSQL, which also holds the job queue. Connected accounts are rebuilt from the broker's own deal records and reconciled against the balance. Patterns come from fixed rules, not a model.

    A 15-chapter specification is the source of truth. Database migrations are generated from its SQL, and 31 architecture decision records explain every trade-off, including the features I said no to.

    Decisions

    1. Modular monolith, two processes. No microservices, no Redis, no Kubernetes. One engineer has to be able to own all of it. ADR-002
    2. PostgreSQL is the job queue. A job commits in the same transaction as the data it's about, so there's no second system to fall out of sync. ADR-005 · 011
    3. Full rebuild on every sync, diff writes. Boring and idempotent. Incremental patching waits for a measured trigger: 50M rows or rebuilds over 60 s at p95. ADR-016
    4. Rejected: trades read from screenshots. Numbers we can't reconcile become statistics we can't defend. ADR-025

    Never

    • The browser never touches the database or the broker connection.
    • A broker password is never kept beyond its single use.
    • Money, prices and R are decimals, never floats. Business logic never reads the clock directly.
    • Tenant isolation is never left to one layer: app checks and Postgres row-level security both apply.

    Measured

    • 41.6 sto rebuild 100,000 trades from scratch; 14.4 s when nothing changedspec §14.2 · measured 7 Oct 2026
    • 31 ADRs · 91 test filesacross 18 packages, a 15-chapter spec and a Truth Set of expected results
    • One gate for everyoneevery pull request, mine or an agent's, passes the same CI checks before it merges

    A-02

    ShelfLink

    Snap a picture, get a shop link, take orders on WhatsApp. Built for sellers in Lagos, Accra and Nairobi, in English and Pidgin.

    Live shelflink.com.ng ↗ Code: private repo

    The problem

    Small sellers in West Africa sell through WhatsApp status and send each customer thirty photos, one at a time. They don't want an app, a dashboard or a monthly fee.

    What I built

    A Telegram bot is the entire seller interface: send a photo with the price under it and it becomes an item on a public shelf. One Cloudflare Worker runs the webhook, the price parser, the English and Pidgin copy, the media proxy and the morning digest. Buyers fill a bag and send the seller one WhatsApp message with the items, links and subtotal.

    Decisions

    1. Telegram as the CMS and media store. Sellers already live there, and storage costs nothing.
    2. One Worker is the whole backend. Webhook, parser, copy, media proxy and cron ship as one deploy, with no server to patch.
    3. No buyer accounts. Checkout is a WhatsApp message, because that's where the sale closes anyway.
    4. Pidgin is a first-class language. Onboarding copy was written in it, not translated into it afterwards.

    Never

    • A buyer never needs an app or an account to order.
    • A seller never needs a channel or a dashboard to open a shop.
    • A seller never retypes a catalogue: every later photo is a new item with Sold, Price, Hide and Delete buttons.

    Measured

    • 25+ live shopsthe largest lists 131 itemsshelflink.com.ng · 24 Oct 2026
    • 15 of 15checks passed by the scripted evaluator at the production cutover to shelflink.com.ng
    • 3 Workers, 1 databasesite, API and www redirect. No servers to patch.

    A-03

    MedLocum Academy

    The e-learning centre inside Medical Locum Jobs: self-paced courses, tests that count, CPD records and verifiable certificates for clinicians.

    Live medlocumjobs.com/courses ↗ Code: employer's repo

    The problem

    I ran these courses by hand first. Lectures lived in Telegram groups, tests were duplicated for every cohort, results were merged in spreadsheets and certificates went out one by one. Every step leaked: duplicate people, unclear retakes, participation marks that were guessed.

    What I built

    Self-paced courses with configurable grading (weighted tests, best attempt, a pass mark per course), partner referral links with a commission ledger, Paystack checkout for fees and transcripts, and certificates learners name once and can download again. A lecturer's Telegram course became 55 lessons through a transcription pipeline and a writer and clinical-editor review.

    Decisions

    1. Unknown values read as "unknown". One drifted enum value in production was crashing whole admin pages. A safe cast ended that class of 500s instead of patching them one by one.
    2. The manual rule is one option, not the rule. Grading is configurable per course, so the old spreadsheet formula survives only where it's still wanted.
    3. Courses ship as data. Each course is a seeder plus files in a private bucket, so it can be reviewed in a pull request and rebuilt.
    4. Audit before launch. I proved each launch blocker with a test that reproduces it, so every fix can be shown to work.

    Never

    • Participation never counts toward a grade unless it was measured.
    • Learners' own messages were never part of the course migration, and the lecturer's written rights came first.
    • A certificate name is never edited in place: a correction rebuilds the PDF and sends it again.

    Measured

    • 55 lessons, 39 with videomoved from a Telegram group into one self-paced course
    • 8 launch blockersfound in a pre-launch audit, each proven with a failing test
    • 2–3 days → minutesfor monthly result collation, with errors cut from 5–10% to zeroResults Compiler · D-01

    A-04

    Xora

    An AI bookkeeper for Nigerian businesses. Xora drafts and people approve. It never moves money, and it never guesses.

    Live demo Watch the demo ↗ Code: private · v1 in build

    The problem

    Most small Lagos businesses run on bank alerts and memory. Accounting software assumes an accountant on staff, and AI bookkeepers post confident entries nobody checked.

    What I built

    Statement import for CSV, Excel, PDF, OFX and QIF, including Nigerian bank layouts, with duplicates removed across overlapping statements. A double-entry ledger with period locks and reversals. Anything Xora can't trace becomes a question to the owner, and answers can become rules. Only owner-confirmed rules post automatically; everything else waits for an approval with a PIN or emailed code.

    Decisions

    1. Questions instead of assumptions. An unexplained transaction goes to an inbox with a one-tap answer, not a "best guess" category.
    2. Every naira has a home. Each bank balance is split into tax owed, money due to others, bills due and what's free to spend.
    3. Reports tie to the trial balance. If they don't add up, the report says so.

    Never

    • Xora never moves money.
    • A rule the owner hasn't confirmed never posts on its own.
    • The chat assistant proposes changes and never posts them.

    Measured

    • 5 statement formatsCSV, Excel, PDF, OFX and QIF, with Nigerian bank layouts
    • 4 rolesowner, admin, accountant and viewer, with step-up approval for sensitive actions
    • A full month, start to finishthe public demo keeps a fictional Lagos company's books on the real software

    A-05

    HORC Research Engine

    A research lab for FX market structure, built to kill ideas before they cost money.

    Private · case study Python · Rust · Pine

    The problem

    Trading ideas are easy to fall in love with and easy to backtest into looking good. I needed a lab where every rule is mechanized exactly, every study is declared before its data is read, and costs get the last word.

    What I built

    A Python engine is the single authority, the oracle. A std-only Rust executor reproduces it byte for byte, about 100 times faster, so big replays are cheap and any drift is caught. Studies are preregistered, run on development data, then read once on a sealed holdout with real spreads. Every verdict, null results included, goes into an append-only ledger. A TradingView indicator draws the certified engine on live charts.

    Decisions

    1. Python defines, Rust replays. The fast path can never quietly change the rules, because parity with the oracle is checked on every change.
    2. Bit-exact float64, no silent tick migration. Normalizing prices to ticks is its own study, run on the oracle first, with every changed event explained.
    3. Fail closed on ambiguity. Two events on the same five-minute bar have no knowable order, so the event ends there. No reading it from candle shape.
    4. Spend tokens before features. The indicator lives under TradingView's 100k compiled-token cap. I merge and delete before I add.

    Never

    • An edge is never claimed before fresh data and real costs.
    • A null result is never repaired after the fact. It's recorded.
    • The Rust engine never introduces a rule.

    Measured

    • 2,055 s → 20 sfull-stack replay, byte-identical to the Python oracle on all 25 panels
    • 22 years of FXdozens of preregistered studies; most were null, and all of them are kept
    • +0.21 R gross, −0.04 R netthe best signal held across 18,000 trades, then failed on reserved data at my real broker cost. Shelved.CZR-MAJ-1 · 24 Oct 2026

    A-06

    Certify

    Cohort certificates with registration links, an approval gate, PDFs with QR checks and email dispatch. In daily use by the course team.

    Internal · in use Laravel · Livewire

    The problem

    Certificates are what participants keep. They have to arrive, carry the right name and stay verifiable, on a host where the disk is wiped on every deploy and no background worker runs.

    What I built

    I extracted the certificate pipeline from the main site into its own app, so it could be deployed and hardened alone. Each cohort gets a registration link, every registration passes an approval gate, approved certificates render on demand, and sending them is a separate, deliberate step.

    Decisions

    1. No queue worker. Every email is sent synchronously. Bulk sends are split into small batches across page requests, so nothing depends on a process that can die quietly.
    2. Signatures live in the database. They're the one asset that can't be regenerated, and the disk is wiped on deploy.
    3. Approval before generation. Nothing is issued automatically.
    4. Additive migrations only. Live cohorts are mid-course, so the schema only grows.

    Never

    • Certificate delivery never depends on a worker staying alive.
    • A send is never able to email the same person twice.
    • The disk is never the source of truth for a signature.

    Measured

    • 0 background workersto monitor, restart or forget about
    • Resumable by designa send survives a reload, a crash or a closed tab
    • Live with real cohortsregistration, approval, PDF, QR check and dispatch, in daily use

    A-07

    groupmemory

    A Telegram community's memory, readable by any member's own AI, with a receipt for every answer.

    Private · v0.2 Python · SQLite · MCP

    The problem

    Big Telegram communities teach a lot and remember none of it. Pasting chats into an AI gives confident summaries with no sources, and nobody can prove who said what.

    What I built

    A consent-first bot archives the group into SQLite, chaining every message to the one before and sealing the chain daily. An MCP server with 26 tools lets a member's own AI search, cite and prove messages. No model runs on the server, so there's no inference bill. Owners can export a cited Course Pack for AI coding agents and get paid in Telegram Stars.

    Decisions

    1. A sense organ, not another AI. The server finds and proves; the member's own AI does the talking.
    2. One process, one SQLite file. Graceful drain, a single-instance lock and encrypted off-site backups that restore themselves onto an empty disk.
    3. Payments without signup. Telegram Stars invoices and subscriptions, recorded in an idempotent ledger.

    Never

    • No model runs on the server.
    • Nothing is archived without consent, and /forgetme really erases.
    • An answer never arrives without the message it came from.

    Measured

    • ~190 MB idle~227 MB peak at 200,000 messages
    • 86 testsincluding the real bot against a fake Telegram API
    • 26 tools · 8 promptsover streamable HTTP and stdio

    Specification · how I work with AI agents

    AI writes a lot of my code. It doesn't decide what's true.

    I run Claude Code every day across about ten projects, with agents in separate worktrees and MCP servers I write myself. Speed is the easy part. These four rules keep the output honest, and each one is enforced by a tool rather than by memory.

    S-1

    The specification is the source of truth

    Database migrations are generated from SQL blocks in the spec. A migration that drifts from the spec fails CI.

    generate-migrations.mjs --check
    S-2

    Boundaries are checked by tools

    The web app can't import the code that unseals credentials; a dependency rule fails the build if it tries. A test fails if banned words reach the trader-facing copy.

    pnpm deps → dependency-cruiser
    S-3

    Tests are evidence, not targets

    Nobody edits a test or an expected value to make it pass. If the engine disagrees with the Truth Set, work stops and the disagreement gets escalated.

    CONTRIBUTING.md · rule 2
    S-4

    Everyone goes through the same gate

    Mine or the agent's, every pull request runs typecheck, lint, dependency rules, unit tests and database tests on a real PostgreSQL before it merges and deploys.

    pnpm typecheck && pnpm lint && pnpm deps && pnpm test:all
